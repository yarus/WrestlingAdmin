# Post-tournament punch-list — 2026-04-28

Проблемы, выявленные пользователем по итогам реального турнира. Решаем по очереди.

## Сквозная архитектурная тема

Несколько пунктов (#1, #3, #5, #10) сводятся к одному и тому же шаблону:
**администратор турнира на главном ноуте вносит изменение → нужно принудительно раскатить его на все ковры/экраны.**

Сейчас архитектура асимметрична: каждый ковёр держит свою копию `.wrt`, а Import тянет только **завершённые матчи** (Pending→Completed). Структурные изменения (длительность раунда, состав сетки, перенос категории, переназначение спортсмена) через текущий импорт не передаются в принципе — они либо игнорируются адаптером, либо «съедаются» при следующем сохранении ковра.

Поэтому большинство пунктов ниже требует:
1. **Экран администратора** на ноуте организатора с операциями над «живым» турниром.
2. **Канал push-обновлений** — расширение существующего HTTP/UNC импорта новым типом сообщения «применить дельту структуры», а не «забрать новые завершённые схватки».
3. **Версионирование/идемпотентность** — у каждой административной правки должен быть id и timestamp, чтобы ковры могли понять «уже применил / надо применить / конфликт».

Спроектируем это до того, как браться за конкретные пункты — иначе сделаем 4 разных механизма синхронизации.

## Список проблем

### #1 — Массовая смена длительности раунда для возрастной группы
**Симптом:** изменили `RoundDuration` (или аналогичный параметр) в Положении турнира — на уже созданные `WrestlingMatch` это не распространяется. Прокликивать каждую весовую категорию в живую неудобно.

**Гипотеза:** длительность раунда копируется в матч в момент генерации сетки и потом живёт независимо. Изменение шаблона на турнире не каскадируется.

**Решение:**
- Операция «применить новые тайминги к матчам категории X / возраста Y» в админ-панели.
- Безопасность: только к матчам со статусом Pending (не трогать уже завершённые).
- Раскатка на ковры через push-канал (см. сквозную тему).

**Сложность:** S (логика) + M (push-канал, общий с #3/#5/#10).

### #3 — Принудительная раскатка изменений сетки на все ковры
**Симптом:** правки в сетке (перепосев, корректировка участников) приходится разносить флешкой и перезапускать программу на каждом ковре.

**Решение:** В админ-панели — кнопка «опубликовать сетку категории X». Push на все ковры, которые подписаны (HTTP/UNC). На стороне ковра:
- Если категория ещё не начиналась — заменить целиком.
- Если категория начиналась — сравнить и применить только структурные правки, сохранить уже отыгранные результаты (если возможно). При конфликте — показать предупреждение и не применять автоматически.

**Сложность:** L. Это и есть главная инфраструктурная работа из «сквозной темы».

**Зависимость:** определяет формат push-канала, который потом переиспользуется в #1, #5, #10.

### #5 — Перенос/переназначение спортсмена между категориями после старта турнира
**Симптом:** спортсмен ошибочно зарегистрирован в категории A, нужно перевести в B. Возможны 3 ветки:
1. **Ни в A, ни в B матчей не было** → удалить из A, добавить в B, перегенерировать обе сетки, раскатить.
2. **В A матчи начались, в B — нет** → в A пометить дисквалификацией/неявкой (его прошлые матчи не идут — но он же только что добавлен, прошлых не будет), в B добавить и (пере)генерировать сетку.
3. **В обеих категориях матчи начались** → пересоздание сетки B с миграцией. Технически непростая операция.

**Решение:** Админ-операция «переназначить спортсмена», которая:
- Анализирует состояние обеих сеток.
- Предлагает применимый сценарий (1/2/3), не даёт пользователю случайно выбрать ломающий.
- Для сценария 3: отдельный диалог с явным выбором — «оставить результаты в A, в B пересобрать сетку», «дисквалифицировать в A, в B зарегистрировать как нового», и т.п.
- Раскатывает изменения push-каналом.

**Сложность:** M-L (логика веток) + общий push-канал.

### ✅ #15 — Выбор сетевого интерфейса для HTTP-анонса при нескольких NIC (DONE)
**Симптом:** На ноутах с двумя сетевыми интерфейсами (например, у Admin: `192.168.1.60` и `192.168.88.x`) `LocalIpAddressProbe.PickDefault` берёт первую попавшуюся 192.168/16 — порядок зависит от энумерации NIC. Может оказаться неверной подсетью, и HTTP-анонс уйдёт с адресом, до которого пиры физически не доходят.

**Решение:** Добавлено `GlobalSettings.AnnounceIpOverride` + `LocalIpAddressProbe.PickAnnounceAddress(override)` (валидирует наличие IP на машине, иначе fallback на `PickDefault`). В `SettingsView` — ComboBox с пунктом «(Авто)» по умолчанию и текущими IPv4. См. блок Done выше.

**Что осталось открытым:** auto-режим всё ещё «первая 192.168/16» — без подсетевого матчинга к получаемым UDP-анонсам. Если 95% пользы снимает ручной override — авто-матчинг вынесем в отдельную задачу при необходимости.

### #14 — Устойчивость Case-2 revert импорта при смене конфигурации источника
**Симптом:** Когда оператор удаляет пир из `ImportSources` или пир меняет формат анонса (например, добавляет/убирает `SelfUncPath`), стампы `WrestlingMatch.ImportCompletionSource` на уже импортированных матчах остаются со старой строкой источника. Если потом тот же пир откатывает результат на своей стороне — Case-2 reverts (`TournamentImporter.cs:223-236`) сравнивает `baseMatch.ImportCompletionSource == plan.Source` и не находит совпадения → откат не пройдёт.

**Подтверждение:** В файлах с реального турнира (`D:\20260426.wrt`, `D:\2026042-этаж16.wrt`) есть стампы на 88.241, но самого 88.241 в текущих `ImportSources` нет. Если 88.241 откатит матч у себя — на этих ноутах локально матч останется Completed.

**Контекст:** концепция «один авторитетный источник на матч» хрупкая — импорт может прийти от разных компьютеров, а во время живого импорта надо решать, какой откат «более поздний». Простое решение «обнулять стамп при удалении источника» не подходит — это ломает другую логику.

**Решение (черновое):**
- Версионировать матчи по `(MatchId, RemotePeerInstanceId, RemoteTimestamp)` — стамп хранит не строку источника, а структуру.
- При откате сравнивать timestamp'ы — принимать только более поздний.
- Стандартный сценарий «пир пропал/переименовался» переходит в «не делаем ничего, потому что нет более позднего сигнала».

**Сложность:** M-L. Требует расширения `WrestlingMatch` (новая структура импорт-метаданных вместо строки), миграции для старых `.wrt` и аккуратной работы с конкурентными источниками.

### #12 — Дисквалификация спортсмена с турнира
**Симптом:** по правилам — все предыдущие результаты дисквалифицированного аннулируются. Также сценарий обоюдной дисквалификации.

**Действие:**
- В `Wrestling.Entities/Bracket/...` найти, как сейчас обрабатывается дисквалификация (вероятно как тип победы).
- Добавить операцию «дисквалифицировать спортсмена с турнира» (в отличие от «дисквалификация в одном матче»).
- Каскад: пройти по всем матчам спортсмена, пометить их как аннулированные, пересчитать места группы, пересчитать командный зачёт.
- Обоюдная дисквалификация: оба борца теряют все результаты.
- Раскатить через push-канал.

**Сложность:** L. Требует аккуратной работы с уже посчитанными местами и командными очками.
